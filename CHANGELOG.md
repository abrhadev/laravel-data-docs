# Changelog

All notable changes to `laravel-data-docs` will be documented in this file.

## Unreleased

### Added

- Conditional requirement attributes are documented. `#[RequiredIf]`, `#[RequiredUnless]`, `#[RequiredWith]`, `#[RequiredWithAll]`, `#[RequiredWithout]` and `#[RequiredWithoutAll]` add a sentence naming the field and value the condition depends on, for example "Required when <b><i>account_type</i></b> is <code>business</code>.", and such a property is published as optional. A condition Laravel Data does not enforce is not published: one followed by `#[Present]`, `#[Required]`, another conditional attribute or an equivalent `#[Rule(...)]`, or one with no compared value.
- `#[Filled]` adds "When included, must not be empty."; `#[Present]` adds "Must be included in the request, but may be empty." on a nullable, uncast `string` property whose key must be sent and where nothing else rejects an empty value; with Laravel's default `ConvertEmptyStringsToNull`, an empty value on any other type is rejected.
- Nullable properties add "A null value is accepted."
- Prohibition attributes are documented. `#[Prohibited]`, `#[ProhibitedIf]` and `#[ProhibitedUnless]` add a sentence stating when the field must not be sent, for example "Must not be sent when <b><i>plan</i></b> is <code>enterprise</code>; the request is rejected if it is.", and `#[Prohibits]` states which other fields sending it forbids. Requirement status is unchanged: a prohibited property that is not nullable, not `Optional` and has no default is still published as required, because Laravel Data still infers `required` for it.
- Exclusion attributes are documented. `#[Exclude]`, `#[ExcludeIf]`, `#[ExcludeUnless]`, `#[ExcludeWith]` and `#[ExcludeWithout]` add a sentence such as "Not validated, and removed from the validated input when <b><i>order_type</i></b> is <code>internal</code>." The field stays documented. The sentence deliberately does not say the value is ignored: Laravel Data builds the Data object from the request payload, so an excluded value still reaches it, unvalidated; only the validator's validated output drops it.
- A property that is required, rejects an empty value and is unconditionally `#[Prohibited]` adds "Note: this field is both required and prohibited, so no request can pass validation." It is not added when an exclusion attribute is declared before `#[Prohibited]`, because Laravel stops validating an excluded field and such a request passes.
- Field comparison attributes are documented. `#[Same]` adds "Must match the value of <b><i>email</i></b>.", `#[Different]` adds "Must differ from the value of <b><i>current_password</i></b>.", and `#[InArray('tags.*')]` adds "Must be one of the values submitted in <b><i>tags</i></b>." A bare `#[InArray('tags')]` is documented as "Must equal the value of <b><i>tags</i></b>.", because only the wildcard form checks membership of an array field.
- `#[Confirmed]` adds "A matching <b><i>password_confirmation</i></b> value must be sent with it." and publishes `password_confirmation` as its own parameter, directly after the property. The companion copies the property's type, location, format and bounds, mirrors its required and nullable status (an optional property's companion adds "Required when <b><i>password</i></b> is sent."), and its example equals the property's. It is not added for a hidden property, for a nested Data property, or when a property of that name is already declared. `#[Confirmed('email_repeat')]` is documented as `email_confirmation`: Laravel Data's `Confirmed` accepts no arguments, so PHP 8.4 discards the name and validation requires `email_confirmation`. PHP 8.3 rejects that declaration outright, for the application and for documentation alike.
- Acceptance attributes are documented with Laravel's exact value sets. `#[Accepted]` adds "Must be sent as one of <code>yes</code>, <code>on</code>, <code>1</code>, <code>"1"</code>, <code>true</code>, or <code>"true"</code>.", `#[Declined]` lists <code>no</code>, <code>off</code>, <code>0</code>, <code>"0"</code>, <code>false</code> and <code>"false"</code>, and `#[AcceptedIf]` / `#[DeclinedIf]` add, for example, "Must be accepted when <b><i>country</i></b> is <code>DE</code>, by sending one of …". `#[Accepted]` and `#[Declined]` properties get an example from their set, unless `#[Example]` gives one or the property is an enum, which keeps a generated case.

### Changed

- **Breaking:** Laravel 11 and Laravel 12 before 12.6 are no longer supported; the minimum is now Laravel 12.6. `#[Password]` is documented from the rules `Password::appliedRules()` reports, and that method first shipped in Laravel 12.6.
- **Breaking:** `ExtendedOpenApiGenerator` is now `final` and extends Scribe's `OpenApiGenerator` instead of `BaseGenerator`. It delegates path items to the Scribe base generator that matches `openapi.version`, so OpenAPI 3.1 output keeps its 3.1 schema shape and `openapi.overrides` are no longer overwritten. Code that subclassed it, or relied on it being a `BaseGenerator`, must register its own generator in `openapi.generators` instead.
- **Breaking:** `custom_types` config bounds (`minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum`, `minLength`, `maxLength`, `minItems`, `maxItems`, `multipleOf`) must be integers. Integral floats and numeric strings such as `5.0` or `"10"` are accepted; any other value, a negative `minLength`, `maxLength`, `minItems` or `maxItems`, or a `multipleOf` of zero or less, throws `InvalidArgumentException` naming the key when the pipeline is built. Previously such values were truncated, so `multipleOf: 0.01` was published as `0`.
- `nullable` is published only where a null value passes validation and the property's PHP type admits it. `#[Required] ?string`, `#[Filled] ?string`, `#[Accepted] ?bool` and `#[Declined] ?bool` now publish `nullable: false`, because Laravel rejects null for each.
- `#[Present]` properties are published as required, because validation fails when the key is omitted. Previously `#[Present]` did not make a property required, so `#[Present] ?string` was published `required: false`. As with any requirement, `Sometimes`, an `Optional` type or a default value still makes the property optional.
- `#[Accepted]` and `#[Declined]` properties are published as required, because validation fails when the key is omitted.
- Field names in descriptions are rendered as `<b><i>field</i></b>` and values as `<code>value</code>`, including in the comparison processors' sentences for field references such as `#[GreaterThan(new FieldReference('min_price'))]`.
- A backed enum is rendered by its case name and backing value wherever it appears in a description, matching the "Must be one of" enum list: `#[RequiredIf('account_type', AccountType::Business)]` now reads "Required when <b><i>account_type</i></b> is <code>Business</code> (business).", and a backed enum default reads "Defaults to <code>Active</code> (active)." This applies to `#[RequiredIf]`, `#[RequiredUnless]`, `#[ProhibitedIf]`, `#[ProhibitedUnless]`, `#[ExcludeIf]`, `#[ExcludeUnless]` and default values. Previously a condition showed only the backing value and a default only the case name. The schema `default` is unchanged and still holds the backing value.
- Fractional numeric bounds are published in the schema instead of being truncated. `#[GreaterThan(0.5)]` publishes `exclusiveMinimum: 0.5`, and `#[Min(0.25)]`, `#[Max]`, `#[Between]` and `#[Size]` on an integer or number field publish `minimum` / `maximum` as declared; an integral float such as `5.0` is published as `5`. Length and item-count bounds are published as integers, a fractional one as the whole number it means. An out-of-range float bound, or a `#[MultipleOf]` that is not a positive integer, is described but not written to the schema. Previously these were truncated, so `#[MultipleOf(0.5)]` published `multipleOf: 0`.

### Fixed

- Validation attributes whose argument cannot be documented no longer fail the whole documentation build. `#[Min]`, `#[Max]`, `#[Size]`, `#[Between]`, `#[Digits]`, `#[DigitsBetween]`, `#[Regex]`, `#[MultipleOf]`, `#[StartsWith]`, `#[EndsWith]` and `#[DateFormat]` given an `ExternalReference`, `INF` or `NAN`, or `#[Digits(0)]`, are now skipped instead of throwing.
- A bare `#[StartsWith]` or `#[EndsWith]` no longer publishes the match-everything pattern `^()` or `()$`.
- A boolean compared value in a `#[RequiredIf]` or `#[RequiredUnless]` sentence is rendered as `true` or `false`. Previously `false` rendered as an empty code span and `true` as `1`.
- The config publish command in the README uses the real tag, `data-docs-config`.
- A subclass of a documented attribute (of `#[Min]`, of `#[Description]`, …) is documented as the attribute it extends (a subclass of `#[RequiredIf]` or the other conditional attributes that emits another keyword, such as plain `required`, is published as required, since it enforces that rule; one that only changes `parameters()` stays conditional), and a subclass of a conditional attribute such as `#[RequiredIf]` is published as optional, as its parent is; before, it was silently ignored. A bare subclass of `#[Prohibited]` or `#[Exclude]` is stated as unconditional, as Laravel enforces it (one that declares its own `getRule()` keeps the conditional wording, since it enforces whatever that returns), and on a required field a bare `#[Prohibited]` subclass gets the note that no request can pass validation. On controller methods, a subclass of `#[Description]` or `#[ResponseData]` is read too, and one `#[Description]` that cannot be instantiated no longer drops the valid ones.
- Controller parameters typed as a Laravel Data `Dto` are documented like `Data` objects; a `Resource` is still ignored, as it is not request input.
- A `#[ResponseData]` class no longer gets a `{field}_confirmation` response field for a `#[Confirmed]` property.
- A custom type processor that leaves the class name as the type no longer publishes it as the OpenAPI type; the property is published as a `string` (`string[]` for an array, with "Each item must be a …" naming the class). An array of a class with no custom type configured or registered is published as an array of strings ("Each item must be a DateTimeImmutable.") instead of a single string.
- A `custom_types` entry missing `type` or `descriptions` throws an `InvalidArgumentException` naming the key, instead of an undefined-array-key error.
- A `null` compared value is stated as the empty string Laravel compares against: `#[RequiredUnless('status', null)]` read "Required unless status is `null`", although Laravel writes the rule `required_unless:status,` and requires the field when `status` is missing or null; it now reads "…is `""`".
- A condition value holding a comma is stated as the values Laravel compares against: `#[RequiredIf('country', 'DE,AT')]` read "Required when country is `DE,AT`", although Laravel requires the field when the country is `DE` or `AT`; it now reads "…is one of: `DE`, `AT`". The same holds for `#[RequiredUnless]`, `#[ProhibitedIf]`, `#[ProhibitedUnless]`, `#[ExcludeIf]`, `#[ExcludeUnless]`, `#[AcceptedIf]` and `#[DeclinedIf]`. A field reference holding a comma is read the same way: `#[RequiredWith('a,b')]` read "Required when a,b is present.", naming a field that does not exist, and now reads "Required when any of a, b is present."; likewise `#[RequiredWithAll]`, `#[RequiredWithout]`, `#[RequiredWithoutAll]`, `#[Prohibits]` and `#[ExcludeWithout]`, while `#[ExcludeWith('a,b')]` names only `a`, the one field Laravel checks. The cross-field attributes read such a reference as Laravel does too: `#[Same('a,b')]`, `#[InArray('a,b')]` and the comparison attributes name `a`, `#[Different('a,b')]` names both, and a condition's field written `'a,b'` (`#[RequiredIf('a,b', 'x')]`, `#[AcceptedIf]`, `#[ProhibitedIf]`, `#[ExcludeIf]`, …) reads the field `a` compared with `b` or `x`, also with no other value (`#[RequiredIf('a,b')]` reads "Required when a is `b`.", where it stated nothing).
- More generated examples pass the field's own rules: a string with a large `#[Min]` (`#[Min(200)]`) gets an example that long, and a `#[Url]` with a `#[Min]` gets a URL long enough; a narrow fractional range such as `#[GreaterThan(0.5), LessThan(0.55)] float` gets a value inside it (`0.51`–`0.54`), as does a range holding one two-decimal value or none (`(0.555, 0.565)`, `(0.001, 0.009)`); a whole-number example on a float field (`#[Digits(18)] float`) is an integer, which `digits` accepts, instead of a float written in exponent form; a fractional or negative `#[MultipleOf(0.1)]` gets a multiple of it, also beside `#[Digits]` on a float and with only an upper bound below the divisor (`#[MultipleOf(0.25), LessThan(0)]`, `#[MultipleOf(0.3), LessThan(1.1)]`); a string field with a pattern and a length bound (`#[Min(15), Uppercase]`, `#[StartsWith('09'), Digits(11)]`) gets an example of that length that every pattern rule accepts, including a prefix and a suffix together (`#[StartsWith('img_'), EndsWith('.png')]`) and a format with a prefix or suffix (`#[Url, EndsWith('.pdf')]`, `#[IP, StartsWith('10.')]`) or with a regex that publishes no pattern (`#[Url, Regex('/\.pdf$/i')]`); patterns such as `\p{Lu}`, named groups and negated classes get an example too, a pattern example is never empty, and a format beside a case rule (`#[Email, Lowercase]`, `#[Uuid, Uppercase]`) gets a value of that format; a string field compared with a range holding no whole number (`#[GreaterThan(0.5), LessThan(0.9)]`) gets a decimal such as `"0.7"`, written to its length bounds (`"0.7000"` for `#[Min(6)]`); a boolean `#[In([0])]` gets the example `0`; an `#[In]` value any of the field's pattern rules rejects (`#[In(['eur', 'USD']), Uppercase]`, or `ab1` in `#[In(['abc', 'ab1']), Alpha, Lowercase]`) is no longer published, stated or drawn, judged by Laravel's own rules (a `#[Regex]` by the regex as declared, flags included), and neither is one a length, numeric bound, divisor, format, date or password rule on the field rejects (`#[In(['ab', 'abcdef']), Max(3)]`, `#[In(['a@b.co', 'bad']), Email]`, `#[In([...]), DateFormat('Y-m-d')]`, a `#[Password]`'s character classes, `#[Accepted]` or `#[Declined]` (`#[In(['on', 'maybe']), Accepted]` publishes only `on` and draws its example from it); a rule that needs the network, `active_url`, `email:dns` or `uncompromised`, and a password's custom rules, which may read the rest of the request, are not checked); when an allowed value, an enum case or the field's example that Laravel accepts is rejected by the field's approximate pattern (`in_progress` beside `#[Lowercase]`'s ASCII pattern, `007` for `#[Lowercase, Digits(3)]`), the pattern is left out rather than making the schema unsatisfiable, the same in every build (an explicit `#[Example]` Laravel rejects decides nothing), also beside a `#[Regex]`; so `in_progress` with `#[Lowercase]` or `café` with `#[Alpha]` is kept; and `#[DateFormat]` and `#[Date]` examples are drawn from fifty years either side of today, so a pattern such as `StartsWith('205')` can be met, and a narrow one such as `StartsWith('2031-05')` is laid over a drawn date; `#[Date, DateFormat('d/m/Y')]` gets a date both rules read, and `#[Date, DateFormat('H:i', 'Y-m-d')]` an example in the format `date` reads, and lists only that format, also when the date rule is written `#[Rule('date')]`; a `#[Regex]` that publishes no pattern (a `/i` flag, `\z`) gets an example drawn from it; a `#[MultipleOf]` on a string field reads "Must be a number that is a multiple of …" and gets a numeric example, a whole multiple padded with leading zeros where a digit rule applies (`#[Digits(3), MultipleOf(3)]` gets `"027"`-style values); a long text example no longer starts or ends with a space, which Laravel's `TrimStrings` middleware would remove; an integer example for a bound beyond the int range no longer wraps to a negative number. A boolean `#[In]` / `#[NotIn]` sentence names `true` and `false`, as a client sends them, instead of `1` and `0`, and a `0` as the string `"0"`; a `#[NotIn]` value a boolean field cannot hold (`'no'`) is left out of its sentence.
- More rules no request can pass are published as a note instead of an ordinary sentence: a negative `#[Size]` or `#[Between]` length or item count (`#[Size(-1)]` on a string), `#[MultipleOf(0)]`, `#[Date]` or `#[DateFormat]` on an array field, and a `#[Password]` rule whose maximum is below its minimum. None of them publishes a bound or format any more. `#[Date]` beside a `#[DateFormat]` the `date` rule never reads (`H:i`, `d/m`) is published as a note too. On an integer field a range with no whole number reads "…which no integer can be, so any integer sent fails validation", since Laravel Data validates an `int` as `numeric` and lets a fraction through.
- `#[StartsWith]` and `#[EndsWith]` read their values as Laravel does: a comma splits a value (`#[StartsWith('a,b')]` published `^(a,b)`, which rejects `bcd`; it now publishes `^(a|b)`), and an empty value is skipped instead of producing a pattern that matches everything. With no value left, Laravel rejects every request, and the field now says so in a note.
- `#[Date]` no longer publishes `format: date`: Laravel's `date` rule accepts any value `strtotime` reads, such as `2024-01-31 10:00:00`. Its example is still a `Y-m-d` date.
- The `#[Ulid]` pattern accepts lower-case ULIDs, as Laravel does, and rejects a first character above 7, which Laravel rejects; before, most generated ULID examples failed the rule.
- `#[IP]` properties get an IP address as their example instead of a random word.
- Parameters are published under the names Laravel Data uses on the wire. A property with `#[MapInputName]`, `#[MapName]` or a class-level name mapper was documented under its PHP name (`firstName`) while Laravel validates the mapped one (`first_name`); request parameters now use the input name, `#[ResponseData]` fields the output name, nested fields are prefixed with mapped names, and a `#[Confirmed]` companion is named after the input name (`new_password_confirmation`).
- OpenAPI 3.0 output (the default `openapi.version`) no longer publishes `exclusiveMinimum` or `exclusiveMaximum` as numbers, which OpenAPI 3.0 defines as booleans. `#[GreaterThan(5)]` published `exclusiveMinimum: 5`; with 3.0 it now publishes `minimum: 5` and `exclusiveMinimum: true`. When an inclusive bound on the same side is stricter, as in `#[Min(8), GreaterThan(5)]`, only `minimum: 8` is published. OpenAPI 3.1 output keeps the numeric form.
- Smaller corrections: `#[GreaterThan(INF)]` and the other comparisons with a non-finite bound, which Laravel reads as a field name, are no longer documented as a numeric bound; a `#[NotIn]` on an array field now also redraws an empty array example, which `not_in` rejects; `#[Url('ftp', 'ftp')]` names the protocol once; the request strategies return no parameters instead of failing when Scribe passes an endpoint with no method; and a `#[ResponseData]` class that is not a Laravel Data class documents no fields instead of reaching Laravel Data's internals.
- On an array of a custom type (`Money[]`), the item constraints its `custom_types` entry or processor sets (`pattern`, `format`, lengths, numeric bounds) are published under `items`, where OpenAPI applies them, instead of beside `type: array`, where they were ignored; the example's items meet them, and an `#[In]` on the field publishes only the values they accept. An attribute's constraint on an array field stays on the field, since Laravel applies it to the array itself.
- Response fields documented with `#[ResponseData]` now carry their schema constraints (`format`, `pattern`, length and numeric bounds, `default`, …) in the OpenAPI spec, as request parameters do, including fields of nested objects and of arrays of Data objects. Previously Scribe built response schemas without them.
- `#[GreaterThan]`, `#[GreaterThanOrEqualTo]`, `#[LessThan]` and `#[LessThanOrEqualTo]` no longer truncate a fractional bound into the schema: `#[GreaterThan(0.5)]` published `exclusiveMinimum: 0`, and now publishes `0.5`. A field reference no longer clears a bound another attribute set.
- When several attributes bound the same field, the strictest bound is published whatever order they are declared in. `#[Min(5), GreaterThanOrEqualTo(3)]` and `#[GreaterThanOrEqualTo(3), Min(5)]` both publish `minimum: 5`; previously the last declared won, so the first published `minimum: 3`. This covers `#[Min]`, `#[Max]`, `#[Between]`, `#[Size]` and the four comparison attributes, for numeric bounds, string lengths and item counts. An attribute can therefore narrow a bound set by a `custom_types` config entry, but no longer loosen it.
- The comparison attributes on string and array fields now describe what Laravel checks. A literal bound compares numbers only, so on a string field `#[GreaterThan(5)]` reads "Must be a number greater than <code>5</code>." (`"9"` passes, `"abcdef"` never does), and on an array field it adds a note that any request sending the field fails validation, because no array passes. A field reference compares string length or item count: "Must be greater than <b><i>name</i></b>, compared as numbers when both values are numeric and by length otherwise." or "Must have more items than <b><i>options</i></b>." Neither type gets a numeric schema bound any more; previously both read "Must be greater than …" and published `exclusiveMinimum` and its siblings on a string or array schema.
- A string field with a literal comparison bound now gets a numeric-string example within its bounds, for example `"7"` for `#[GreaterThan(5), LessThan(10)]`, instead of a random word the rule rejects. A string field compared with another field keeps its generated word. The example also meets `#[Min]`, `#[Max]`, `#[Between]` and `#[Size]` on the same field, which Laravel still applies to the string's length: `#[GreaterThan(5), Min(4)]` gets a four-digit example such as `"4821"`, and a range too small for the length is zero-padded, such as `"0023"` for `#[LessThan(50), Min(4)]`, which Laravel still compares as the number 23.
- Generated examples meet fractional bounds. A fractional `#[Min]`, `#[Max]`, `#[Between]`, `#[Size]` or comparison bound on an integer, number or numeric-string field is respected by the example: `#[LessThan(0.5)] int` gets `0` or below instead of a value from 1 to 100, and `#[GreaterThanOrEqualTo(0.125), LessThanOrEqualTo(0.135)] float` gets `0.13`. When several bounds apply, the example uses the strictest.
- A fractional `#[Min]`, `#[Max]` or `#[Between]` on a string or array field publishes the whole-number length or item-count bound it means, and the example meets it: Laravel reads `#[Min(2.5)]` as at least 3 characters or items and `#[Max(2.5)]` as at most 2, so they publish `minLength: 3` and `maxLength: 2` (or `minItems` / `maxItems`). Previously they were described but not published. A negative length or item-count bound is no longer published: `#[Min(-1)]` on a string published `minLength: -1`, which is invalid OpenAPI.
- A fractional `#[Size]` on a string, array or integer field, which Laravel never lets pass because a length, count or integer is never 2.5, is now published as a note: "Note: must have exactly <code>2.5</code> characters, which no string can have, so any request that sends this field fails validation." It publishes no bound; previously it read "Must have exactly <code>2.5</code> characters." with `minLength: 3` and `maxLength: 2`. A `#[Size(2.5)]` on a number field is unaffected. The same applies to a `#[Between]` with no whole number in its range, such as `#[Between(2.2, 2.8)]`, or a reversed one, such as `#[Between(5, 2)]`: on a string, array or integer field it now reads "Note: must be between <code>2.2</code> and <code>2.8</code>, which no integer can be, so any request that sends this field fails validation." and publishes no bound, where it previously published contradictory bounds. A reversed `#[Between(5, 2)]` on a number field, which no number meets, gets the same note ("which no number can be") instead of `minimum: 5` and `maximum: 2`.
- A generated string example meets its length bounds: a short word is padded with random letters up to `minLength`, and a long one cut to `maxLength`. Previously `#[Min(3)]` could get a two-letter word.
- A prohibition or exclusion sentence is no longer published when a later `#[Rule(...)]` replaces the attribute. Laravel Data drops an earlier rule of the same class, so `#[ProhibitedIf('plan', 'enterprise'), Rule('prohibited_if:role,admin')]` enforces only the `role` condition but still published "Must not be sent when <b><i>plan</i></b> is <code>enterprise</code>; …", and `#[Exclude, Rule([new ExcludeIf(...)])]` still published the unconditional exclusion. A later rule of another class keeps the sentence, and `#[Required]` or `#[Present]` never withhold it; a later equal rule is documented once, in the attribute's place.
- `#[Regex]` publishes an OpenAPI pattern a consumer can use: `#[Regex('/^[a-z]+$/')]` published `pattern: /^[a-z]+$/`, whose slashes an OpenAPI consumer reads literally, so no value Laravel accepts matched it; it now publishes `^[a-z]+$`. Any delimiter PHP accepts is stripped, including `#…#`, `~…~` and bracket pairs such as `{…}`. The `D`, `S`, `X`, `U`, `r` and `u` modifiers are kept, `A` publishes `^(?:…)`, and escapes are respelled where the two regex dialects differ (`#a\#b#` publishes `a#b`). A regex OpenAPI cannot express exactly (a flag such as `/…/i`, `m`, `s` or `x`, `\w`, `\d` or `\b` under `u` (Unicode classes in PHP, ASCII in ECMA-262), PCRE-only syntax such as `\A`, `(?i)`, `a++` or `[[:alpha:]]`, a backreference, which ECMA-262 matches as empty when its group did not take part, or a quantified lookaround such as `(?=a)?`) publishes no pattern; its sentence still quotes the regex as declared. A string field with both a format and a pattern now gets an example that matches the pattern: `#[Email, StartsWith('a')]` gets an email starting with `a` instead of an email the published pattern rejects, and when no format example can match (`#[Email, Alpha]`), the example follows the pattern.
- `#[DateFormat]` documents every declared format, not only the first. It reads them as Laravel does, so a comma splits a format, and leaves out formats no value can match (`c`, `r`). An OpenAPI `format` is published only when all formats map to it exactly (`Y-m-d`, `Y-m-d\TH:i:sP`, `Y-m-d\TH:i:s\Z`, `H:i:s`). The example is generated from the declared PHP format, so it passes the `date_format` rule, and matches a pattern on the same field where some date can (`#[DateFormat('Y-m-d'), StartsWith('20')]`). A `DateFormat` no value can match is published as a note, and `date-time` examples use an RFC 3339 `+00:00` offset.
- `#[Digits]` and `#[DigitsBetween]` are published in the form each type reads. A `string` field gets a digit pattern and a length instead of a numeric range, so its example is a digit string that passes the rule and leading zeros count. An `integer` or `number` field gets the range of whole numbers with that many digits (`#[Digits(1)]` now includes 0), tightened against other bounds instead of overwriting them; a float also gets `multipleOf: 1`. A bound an int cannot hold (from 19 digits) is no longer published as an overflowed value. A reversed `#[DigitsBetween(5, 2)]` is published as a note that any request sending the field fails validation, with no bound.
- `#[Url]`, `#[ActiveUrl]`, `#[Json]` and `#[Password]` properties get an example that passes their rule. Previously `#[Url]`, `#[ActiveUrl]` and `#[Json]` got a random word, and a `#[Password]` example could miss a required character class or fall short of the minimum. URL examples are `https://` URLs on `example.com`, `example.org` or `example.net`, which resolve, so `#[ActiveUrl]` passes too; `#[Url('ftp')]` gets an `ftp://` URL on the same hosts, which also meets any pattern, `#[NotIn]` or length bound on the field: `#[Url('ftp'), StartsWith('ftp://example.org/')]` gets a URL starting with it. Arguments are now documented: `#[Url('https')]` reads "Must be a valid URL using the <code>https</code> protocol.", `#[Email('rfc', 'dns')]` names each validation mode, and `#[Password(min: 16, mixedCase: true, numbers: true)]` reads "Must be a password of at least <code>16</code> characters containing at least one uppercase and one lowercase letter and at least one number." and publishes `minLength: 16`. `#[Password(default: true)]` is documented from the application's `Password::defaults()`.
- An attribute a later same-class `#[Rule(...)]` replaces is no longer documented, in any family. Laravel Data drops an earlier rule when a later declaration adds one of its class, so `#[Min(5), Rule('min:3')]` enforces only `min:3` but published "Must have minimum <code>5</code> characters." and `minLength: 5`; the same held for `#[Email]`, `#[Regex]`, `#[Same]`, `#[DateFormat]`, `#[Digits]`, `#[GreaterThan]` and the other validation attributes. Such an attribute now publishes no sentence, bound, format, pattern or example. It is still documented when the later rule has another class or is declared before it. The replacing rule is documented instead: `#[Min(5), Rule('min:3')]` publishes "Must have minimum <code>3</code> characters." and `minLength: 3`, and an equal later rule is documented once, in the attribute's place, so `#[Prohibited, Rule('prohibited')]` or `#[Filled, Rule('filled')]` states its sentence once rather than twice.
- Validation rules declared as `#[Rule(...)]` strings are documented. A rule string is expanded the way Laravel Data expands it and documented exactly like the attribute it stands for: `#[Rule('min:3')]` publishes the same sentence and `minLength` as `#[Min(3)]`, and the same holds for `email:dns`, `url:https`, `regex:…`, `date_format:…`, `digits:…`, `gt:…`, `same:…`, `accepted`, `required_if:…`, `prohibited_if:…` and the other keywords with a documented attribute; `#[Rule('confirmed')]` publishes the confirmation companion. `#[Rule('min:3|max:9')]` documents both rules. A rule string is read at its own position, so a later `#[Present]` or a later same-class attribute takes effect as it does at runtime. Previously every rule string was ignored. A bare `#[Rule('exclude')]`, which Laravel Data keeps as a plain rule but Laravel still enforces, is documented like `#[Exclude]`: it stays unconditional when a conditional `#[Exclude]` follows, and it withholds the "no request can pass validation" warning of a later `#[Prohibited]`, as an exclusion does. Keywords with no documented attribute yet, such as `not_regex`, are still not documented.
- `#[In]` and `#[Rule('in:…')]` are documented. The accepted values are published as the OpenAPI `enum` list, typed to the field (`#[In([1, 2, 3])] int` publishes `[1, 2, 3]`, and `#[In([true, false])] bool` publishes `[true, false]`; a `0` on a boolean field is left out of the list, since only the string `"0"` passes it), with "Must be one of: <code>pending</code>, <code>shipped</code>." ("Each item must be one of: …" on an array), and the example is one of them. Values compare as Laravel compares them: as exact strings, a backed enum case by its value and a pure one by its name; a declared value a numeric field can never have is left out, including one not written the way its number prints (`'01'` on an integer or `'1.50'` on a float field, which Laravel's exact string comparison rejects when `1` or `1.5` is sent). On a property typed as a PHP enum, the published list and its sentence keep only the cases the `#[In]` allows, because Laravel Data enforces both. An empty `#[In([])]`, or one that allows no case of the enum, is published as a note that any request sending the field fails validation. An `#[In]` holding an external reference is not documented.
- `#[NotIn]` and `#[Rule('not_in:…')]` are documented. On their own they read "Must not be one of: <code>admin</code>, <code>root</code>." and publish no allowed-value set. With an `#[In]` on the same field, in either declaration order, the published set and its sentence leave out the rejected values, so `#[In(['pending', 'shipped', 'cancelled']), NotIn(['cancelled'])]` publishes `['pending', 'shipped']`; on a PHP-enum property the rejected cases are dropped. On an array field Laravel only rejects an array whose items are all forbidden, so it reads "Must include at least one item that is not one of: …" and never narrows the item set. A generated example the `#[NotIn]` rejects is redrawn. The allowed-value sentence of `#[In]` is now written after all attributes are applied, directly after the type sentence.
- A subclass of `#[RequiredIf]` or another conditional attribute that overrides `keyword()` is documented as the rule it emits. One switched to a sibling rule reads that rule's condition: a `RequiredIf` subclass emitting `required_unless` read "Required when mode is x.", the inverse of what Laravel enforces, and now reads "Required unless mode is x."; one emitting a rule these sentences cannot state (plain `required`, `present_if`, `required_if_accepted`, `missing_with`, …) gets no condition sentence. One emitting another of Laravel's conditional rules (`required_if_accepted`, `required_if_declined`, `present_if`, `accepted_if`, …) is published optional and, on a nullable type, nullable, as Laravel accepts omission and null while the condition is off; it was published required and not nullable. `present` demands the key but accepts null, and `filled` and `missing` reject a value but not an absent key.
- `#[Declined]` beside an `#[In]` set on a boolean field no longer drops `false`: `#[In([true, false]), Declined] bool` publishes and exemplifies `false` instead of claiming that no value is allowed. `#[Accepted]` and `#[Declined]` on an enum-typed property publish and exemplify only the cases the rule accepts (`yes`, not `no`); an enum with no such case is documented as accepting no value.
- An approximate pattern (`#[Lowercase]`'s `^[a-z]+$`, …) is no longer dropped because of an enum case or an explicit `#[Example]` that Laravel rejects for a length or numeric bound or the `#[In]` set, and an array custom type's approximate `items.pattern` is left out when a published `#[In]` item fails it.
- A `#[Regex]` example always matches its own pattern: it is drawn by the package's own pattern reader, so `{4,}`, lookaheads such as `(?=.*\d)`, `(?i)`, nested groups, `\x41`, `\P{L}` and negated classes such as `[^\w]` or `[^[:alnum:]]` no longer give examples such as `9{4,}`. An `#[Email]` with a domain suffix (`#[EndsWith('@corp.com')]`, `#[Regex('/@corp\.com$/')]`) gets an address at that domain, and a `#[Url]` or `#[IP]` with a prefix or suffix beside `#[Lowercase]` or `#[Uppercase]` gets a valid example, with the same published pattern in every build.
- A numeric string with a `#[MultipleOf]` gets an example its pattern rules accept: with a digit rule, a `\d` regex or a prefix (`#[MultipleOf(5), Regex('/^\d{3}$/')]`, `#[Digits(3), MultipleOf(1.5)]`) a whole number padded with leading zeros, never a decimal or a value ending in a bare `.`; `0` when that is the only multiple that fits (`#[MultipleOf(1000), Max(3)]`, `#[MultipleOf(5), LessThan(3)]`); and a multiple within a one-character length for a fractional divisor (`#[MultipleOf(0.7), Max(1)]`). A number field with a divisor larger than 100 (`#[MultipleOf(250.5)]`, `#[MultipleOf(-500)]`, `#[Min(1), MultipleOf(500)]`) gets a multiple as its example.
- An array example has as many items as `#[Min]` or `#[Size]` asks for, more than three included, repeating enum or `#[In]` values when there are fewer.
- A nullable array request field (a `?array` property, in the body, nested or in the query) is published as nullable on the array itself (`nullable: true` on OpenAPI 3.0, `type: ["array", "null"]` on 3.1) instead of on its items, so the spec accepts the `null` that Laravel accepts and no longer accepts `[null]`.
